# Coordinator context budget and succession

You are the only session in a run whose context is never disposable. Each phase worker
gets a fresh session and ends. You persist across the whole plan, so you are the one whose
context rots, and a rotted coordinator fails quietly: it accepts a phase result it no
longer has the context to judge.

So you don't run to exhaustion and you don't rely on compaction. You check a number at
phase boundaries. When it crosses your gate, you **hand the run to a successor
coordinator and stop**.

This file is backend-neutral. The backend's own commands for each step (opening the
successor's terminal, sending its first line, confirming the takeover, and telling
whether you can launch at all) are in the dispatch backend's "Coordinator succession"
section: §9 of the dispatch file that SKILL.md's "Contracts to load first" names. Below,
`ctxcheck` means `python3 <ctxcheck_path>`, the absolute path recorded in
`run-state.json`. "Generation" counts coordinators (1 is the one
the user started). It is never used for a phase's legs.

## When to check

Check **only at a boundary where no worker is in flight**:

- after a phase completes and its worker is released (loop step 8), **before** loop
  step 2 flips the next phase to `[running]`;
- after a continuation leg is released, before the next leg's task is created.

Never check mid-phase, and never on a timer. The check is one plain call, because you
armed yourself at the start of the run:

```bash
ctxcheck ; echo $?        # 0: carry on. 10: over the gate. 3: no budget on this runtime.
```

On exit 10:

- **If the work left is the last phase (or the rest of the phase in flight, when it is
  the last), finish it.** A succession costs a fresh session's startup and
  re-orientation. Spending that to save one phase is a bad trade. Log the overage in
  `run-log.md` and carry on, without checking again.
- **Otherwise, hand off now** (below). A check placed at the boundaries above can't find
  a worker in flight. If the backstop hook warns you mid-phase, finish the phase in flight
  first: never hand off with a worker running, because the successor would inherit a
  dispatch it never saw start.

## Handing off (you are generation G)

### 1. Can you launch a successor?

Before you write anything, run the backend §9 probe for "am I inside a backend terminal",
then `ctxcheck launch-command --json`. Both are read-only. `launch-command` walks your own
process ancestry, finds your agent CLI, and prints the command line that starts a fresh
session of it (resume arguments and the initial prompt stripped). It exits 3 when no agent
ancestor is found.

If the probe fails, or `launch-command` exits non-zero, you can't launch: still do steps
2-5, then take the **fallback** in step 9.

### 2. Write the handoff note

When the backend has an inbox, first settle it per the backend's §9: acknowledge the
deliveries you have already processed (the last completion report among them), so nothing
you handled is replayed to the successor and the takeover wait in step 7 can block. This
is the last acknowledgement you make. A backend with no inbox has nothing to settle; its
§9 says so.

Then write `<runs dir>/coordinator-handoff.md`, overwriting any note an earlier generation left
(those are summarized in `run-log.md` and `handoffs[]`). Write it for an agent that has
never seen this run:

- **Your generation G**, the successor's generation G+1, the absolute plan path, the runs
  dir, the backend run id, and the run-config branch and cwd.
- **Phases done and phases remaining**, by number. For each done phase, say what it
  actually landed (its commit SHA from the outcome record), not what the plan said it
  would land.
- **Any phase mid-continuation**: its number, the leg that runs next, and the path of
  `<runs dir>/phase-N-continuation.md` waiting for that leg. A successor that misses this
  restarts a phase whose edits sit uncommitted in the worktree.
- **The failure counter per phase**, and any `phase-N.txt` regenerated by a failed
  attempt. The successor retries with that file as it stands, not a fresh assembly.
- Anything the plan doesn't say: a question the user answered in this session, a
  workaround, a retry and why, a backfilled outcome record, a worker left retained.
- Live facts the successor can't infer, such as the branch head SHA.
- Explicitly, **what you have not verified**.

This note is the only thing that survives you. What you learned and didn't write here is
lost.

### 3. Record the handoff in run state

Write `run-state.json` atomically (temp file in the same directory, then rename):

- `coordinator_generation` stays G.
- `takeover_pending: G+1`.
- Append `{generation: G, at_pct, after_phase, at}` to `handoffs[]`. `at_pct` is the
  `used_percentage` from `ctxcheck --json`, and `after_phase` the last phase completed.

Append one line to `run-log.md` too. **All of this happens before the successor is
launched**, so the successor never reads a state that doesn't expect it.

### 4. Stop acknowledging

When the backend has an inbox: from here on, **never acknowledge a backend delivery**,
and don't act on one. Anything that arrives now stays unacknowledged, so the successor
receives it on replay. A message you ack now is a message nobody acts on. A backend with
no inbox has nothing to hold back; go on to step 5.

### 5. Disarm

```bash
ctxcheck --disarm
```

Disarm before the successor starts. Otherwise the backstop keeps warning a session that
no longer drives anything.

### 6. Launch the successor

Follow the backend's §9. It opens a fresh agent terminal in the same checkout running
`launch-command`'s `shell_command`, waits for the agent's interface to be ready, and
sends it **exactly one line**. Every newline submits early through a terminal:

```text
Use the run-plan skill on <abs plan path>. You are coordinator generation G+1 taking over a live run; read <runs dir>/coordinator-handoff.md first.
```

`shell_command` is your own command line, minus session-resume arguments and the initial
prompt. It keeps your launch posture (permissions, sandbox, model) intact. A command
built from the agent name alone gets different defaults, and the successor may stop for
confirmation on every action.

### 7. Confirm the takeover

The successor's first backend act rebinds the run to its own terminal, which fences you
when the backend has fencing. Right after that it records
`takeover: {generation: G+1, at}` in `run-state.json`. Wait for that per the backend's §9
(one bounded wait of about ten minutes). **Either** of these confirms the takeover:

- the backend reports that you were fenced (the run now belongs to another terminal);
- `run-state.json` shows `takeover.generation == G+1`. In that case any later backend call
  you make fails as fenced or unbound; that is expected.

A backend with no fencing has nothing to report, so it confirms by `run-state.json`
alone: its §9 polls the file, and from then on you treat the run as the successor's.

Re-read `run-state.json` after the wait returns, whatever it returned.

### 8. If neither arrives

Read the successor's terminal **once** (bounded, per the backend's §9). This is for
diagnosis only:

- **A permission or trust dialog** is on screen. Only a person can clear it. Tell the
  user what it shows and give them the one line from step 6 in case its composer is
  empty after they clear it. **Don't re-send it yourself.** Leave `takeover_pending` set
  and end your turn. Once the dialog is cleared, the successor takes over by itself.
- **The composer is still empty** (the line was swallowed while the agent was booting).
  Re-send the line once, then wait once more as in step 7.
- **Anything else, or still no takeover after the re-send**: the succession failed. Tell
  the user what you saw. Re-arm yourself with the same flags you armed with at the start,
  clear `takeover_pending` (atomically), and mark the last `handoffs[]` entry
  `outcome: failed`. Then ask the user whether to carry on over budget or stop for a
  manual restart, and end your turn on that question. If the successor's terminal is
  still open, name it: a successor that wakes later finds `takeover_pending` cleared and
  stands down.

### 9. Finish

- **On success**: report in one short paragraph: generation G+1 now drives the run, you
  handed off at `at_pct`% after phase `after_phase`, and where its terminal is. Then
  **end your turn.** Do not supervise the successor, wait on the run, acknowledge,
  release or dispatch anything. Two coordinators bound to one run is the failure this
  whole procedure exists to prevent.
- **Fallback** (step 1 found you can't launch, for example outside a backend terminal or
  on an agent `launch-command` doesn't recognize): don't launch anything. Tell the user
  the run is paused at a phase boundary, that the note is at
  `<runs dir>/coordinator-handoff.md`, and that they should open a fresh session in the
  run's cwd and run the run-plan skill on the plan path (Claude Code:
  `/run-plan <plan path>`). That session takes over as the successor (below). End your
  turn.

## Taking over (you are the successor)

Step 0 of run-plan sends you here when `run-state.json` has `takeover_pending` set:

- **Your first line names generation `takeover_pending`**: you are that generation.
- **Your prompt names no generation** (the user re-ran run-plan after a fallback, or by
  hand): confirm once with the user that the previous coordinator has stopped. Then you
  are generation `takeover_pending`.
- **Your first line names a different generation, or `takeover_pending` is unset**:
  this succession was abandoned. Don't touch the run. Tell the user and end your turn.

Then, in order:

1. **Read the handoff note**, `<runs dir>/coordinator-handoff.md`, before anything else.
2. **Rebind the backend run** recorded in `run-state.json` to your terminal, per the
   backend's §9 and §1. Never create a new run: a second run splits the task history.
3. **Acknowledge the takeover right away**, because the predecessor is waiting on it.
   Atomically write `takeover: {generation: <you>, at}`, set `coordinator_generation` to
   your generation, and clear `takeover_pending`. Log it in `run-log.md`.
4. **Skip what an earlier generation already settled.** Skip Step 1's confirmations and
   the resume rule that a `[running]` tag means "confirm with the user" (the tag is your
   predecessor's, and it is live). Never re-normalize the plan, and never re-ask the
   run-config. Reuse `ctxcheck_path` from `run-state.json`.
5. **Reconcile** the backend's task list, the plan's tags and the `legs` in
   `run-state.json` against the note. **Recorded state wins** where they disagree: the
   note is a predecessor's account, the records are what happened. When the backend
   has an inbox, then process the unacknowledged batch your predecessor left you,
   validating each message against the active dispatch ids as usual.
6. **Arm yourself.** The marker is per session, so it didn't come with you. On Claude
   Code invoke the context-budget skill first, then arm as SKILL.md "Context budget"
   says, with the inherited gate (`coordinator_handoff_pct`, when set).
7. **Resume** at the first non-`[done]` phase, or at the mid-continuation leg the note
   names, keeping each phase's failure counter. Don't re-plan, and don't re-dispatch a
   phase the records show as done. **Don't check at the boundary you resume at**: your
   predecessor already checked it, and that check is why you exist. Dispatch first; your
   first check is at the next boundary.

You inherit the same budget and start at a few percent, not zero: reading the note and
the records costs something. Check at your own boundaries and hand off again when you
cross the gate. A third generation is fine, and far cheaper than one bad acceptance.
Skipping the inherited boundary is what guarantees each generation dispatches at least
once. Without it, a successor whose takeover alone crosses the gate would hand off again
before doing anything, and so would the next one.
